# Resolver o workflow na ferramenta escolhida

Use o destino fornecido na sessão ou no perfil privado. Descubra identificadores pelos recursos autorizados atuais; não distribua IDs ou links reais dentro da skill.

## Trello

Confirme board, fila de aprovação, conclusão e correção. Prefira a ordem atual da lista. Listas do sistema e do site podem ter nomes parecidos: não troque uma pela outra. A movimentação para uma lista de conclusão não arquiva o card nem marca um checklist como concluído.

Respeite a preferência de acesso antes de ler: alguns conectores renderizam automaticamente uma prévia grande do card no chat. Suprimir o payload não garante removê-la. Quando o usuário pedir só resumo e link ou determinar Chrome, use a UI do navegador conectado também nas leituras; não repita chamadas do conector tentando ocultar o bloco. Não prometa recolher uma prévia sem um controle confirmado. Se o acesso escolhido falhar, ajude a reconectar em vez de trocar silenciosamente de canal.

## GitHub

Confirme repositório, issue e, se pertinente, projeto e campo Status. Não suponha que encerrar issue muda Projects, nem que mover no Projects encerra a issue. Use somente as operações que existem nas ferramentas atuais. Se o status depende de uma operação indisponível, informe essa parte pendente e não use label/fechamento como substituto silencioso.

O último comentário do solicitante e as respostas posteriores continuam definindo a rodada. PR, merge, checks ou deploy são entrega declarada/evidência técnica, não prova automática do comportamento no produto. Aplique a primeira conferência e o veredito no mesmo fluxo.

Se faltarem destinos ou houver opções concorrentes, peça apenas o dado essencial. Não crie board, projeto ou estado como fallback, nem migre Trello para GitHub sem pedido.
